RolidSCP is a fast two-panel file manager for local disks and remote servers over SFTP, inspired by WinSCP and Total Commander, written in Rust and native on Linux.

**This is a beta release.** It is used daily by its author, but expect rough edges. Please report bugs in Issues. Security problems should be reported privately, see [SECURITY.md](https://github.com/MrRolid/RolidSCP/blob/main/SECURITY.md).

## New in 0.9.1

### Server keys: two lists, `~/.ssh/known_hosts` only read

- Server keys are checked against two lists: the program's own, `~/.config/rolidscp/known_hosts`, and OpenSSH's `~/.ssh/known_hosts`. **The program no longer writes to `~/.ssh/known_hosts`**: a key you trust goes to its own list. Keys trusted with earlier versions stay in `~/.ssh/known_hosts` and still count.
- **When the two lists disagree about a server** (one has the key the server sent, the other a different key of the same type), the program does not connect. The message names both files and lines; ask the server's administrator which key is right and delete the wrong line.
- `~/.ssh/known_hosts` is now read by the program itself, as OpenSSH reads it: names separated by commas, hashed names, wildcards (`*`, `?`), negation (`!`), tabs, and `@revoked`, which refuses a key for every server. A line the program does not understand (a key type it does not know, `@cert-authority`) is skipped instead of making the whole file unusable.
- The key types already known for a server are asked for first, as OpenSSH does: a server with a known ECDSA or RSA key that adds an Ed25519 key is no longer taken for an unknown server.
- The terminal (**Ctrl+P**) checks the same two lists.
- Tested against an in-process server for every case (a key in one list, in the other, in neither, changed, revoked, the lists disagreeing, a list that cannot be read) and against a real OpenSSH server with two host keys.

### Jump hosts

- **Connect through** in the server manager: a saved server can be reached through another saved server, a jump host (ProxyJump in OpenSSH). The program first connects to the jump host, with its own key or saved password, and from there to the server. The server's address is then the one the jump host sees, for example an address in its local network.
- **The keys of both servers are checked**, against both lists of known servers. A question about an unknown key says whether it is the jump host's or the server's.
- A jump host can have a jump host of its own, at most four in a row; a choice that would make a loop is not offered.
- **After a drop-out** the connection is made again the same way, through the jump host, without asking. A jump host with a saved password needs the master password like the server.
- **The terminal (Ctrl+P)** goes the same way: `ssh` with a `ProxyCommand` of `ssh -W` and the same strict key check for every server. Saved passwords of the server and of the jump hosts are passed by the one-time helper, each to its own server's question.
- A saved server that others go through cannot be deleted until they get another way; a server whose jump host was deleted in another window is not connected directly instead.
- Tested against two and three real OpenSSH servers on one computer: listing and transfers through the jump host, both keys unknown, changed or accepted one after the other, the jump host refusing the key, nothing listening at the server's address, and the line to the jump host cut while connected. The terminal command was run for real through one and two jump hosts, with the lists of known servers in a folder whose name has a space and a `%`.

### Trash for local files

- **F8 moves files on this computer's disks to the trash** of the desktop, the one Files, Dolphin, Thunar and Caja show and restore from (the FreeDesktop.org trash). The question says "Move to the trash", the job in the queue says so too.
- A file on another disk goes to that disk's own trash (`.Trash/<uid>` when the administrator made one, else `.Trash-<uid>`), the way file managers do; nothing is copied across disks. Where no trash can be used, a read-only disk for example, nothing is deleted and the message says so.
- **Shift+F8** (and Shift+Delete, File → Delete permanently) deletes permanently, as F8 did before. Files on servers are always deleted permanently, with the question saying ON THE SERVER.
- The trash can be turned off in **Settings → Copying and moving**; then F8 deletes permanently, as in 0.9.0.
- Tested with the trash in the home folder and on another disk: names that need encoding, the same name trashed several times, a link (moved itself, not what it points to), a folder with its contents, and a folder the file cannot be taken from (nothing moved, nothing left in the trash).

### Drag and drop on Wayland (issue #1)

On Wayland, files cannot be dragged to or from other programs yet, in either direction: the window library the program is built on (winit 0.30, used by eframe) has no drag and drop there. Its next version has it, and native support comes when eframe moves to it (planned for 1.0). Until then:

- **Settings → Drag and drop → On Wayland, use X11 (XWayland)** shows the window through XWayland, as an X11 window, after a restart. Dragging then works wherever the desktop passes drags on between X11 and Wayland programs. It is off by default, and the setting says what you lose: **text is less sharp with fractional scaling** (125 %, 150 %), and **other X11 programs can read what you type in the window, the master password too**; a Wayland window keeps programs apart. Programs started from RolidSCP (the editor, a terminal) stay on Wayland.
- Without the setting, once from a terminal: `WAYLAND_DISPLAY= rolidscp`, or `WAYLAND_DISPLAY= ./RolidSCP-0.9.1-x86_64.AppImage`.
- The first time files are dragged out of the window on Wayland, the line at the bottom says that it does not work, with **What to do…**. **Help → Drag and drop on Wayland…** explains it all, with what the window runs on now.
- Tested in a nested GNOME compositor (mutter 48) with a Wayland program on the other side: dragging works both ways, the `.deb` and the AppImage, files in and out. In a nested KDE Plasma compositor (KWin 6.3) files could be dragged into the program but not out of it, the same as from other X11 programs; weston passes no drags between X11 and Wayland programs at all.

### Fixed

- **A drag out to another program could end without a drop.** When the desktop hid its target window at the moment the button was released (KWin does, for drags to Wayland programs), the program found no target and left the drop undone. It now drops on the last target, as GTK and Qt do. A test with a real X server and such a target checks it.

## Requirements

- Linux on 64-bit x86 (amd64 / x86_64) with glibc 2.35 or newer: Debian 12 and newer, Ubuntu 22.04 and newer, current Fedora, openSUSE Leap and Tumbleweed, or another distribution with the AppImage
- X11 session recommended. On Wayland, drag and drop to and from other applications works only through XWayland (see above)

## Known problems

- On Wayland, drag and drop to and from other applications needs XWayland (Settings → Drag and drop → On Wayland, use X11), with less sharp text at fractional scaling and no separation from other X11 programs. Native support waits for eframe on winit 0.31 (planned for 1.0).
- A server that refuses a second SFTP channel gets folder listings through the library's own path, which has no limit on the number of entries.
- Sparse files lose their holes when copied.
- ACLs and extended attributes are not copied (planned for 0.9.5).
- A window of the program that is left alone takes the settings and servers saved by another running copy only at the next mouse move or key press. Nothing is lost: every save merges both.
- Not tested yet: a Windows server and a NAS.

## Install

Check the downloads first. With the release key (fingerprint `9B4B 4478 C213 BD34 3FC2  92C5 2EC7 4F7C CADB 33A2`), the signature and the checksums in one folder:

```sh
gpg --import release-key.asc
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
```

- Debian, Ubuntu, Linux Mint: `sudo apt install ./rolidscp_0.9.1_amd64.deb`
- Fedora: `sudo dnf install ./rolidscp-0.9.1-1.x86_64.rpm`
- openSUSE: `sudo zypper install --allow-unsigned-rpm ./rolidscp-0.9.1-1.x86_64.rpm`
- Other distributions: `chmod +x RolidSCP-0.9.1-x86_64.AppImage` and run it (needs FUSE). The AppImage of 0.9.0 updates itself to this one with AppImageUpdate (`appimageupdatetool RolidSCP-0.9.0-x86_64.AppImage`).
